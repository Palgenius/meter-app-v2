1. OVERVIEW
================================================================================

meter-app-v2 is a Python application that runs on an Orange Pi Zero 3 (ARM64,
2GB RAM) as a systemd service. It:

  - Reads electrical meters via RS485 Modbus RTU or Serial JSON
  - Stores readings in SQLite (WAL mode) for crash safety
  - Aggregates data into 15-minute windows
  - Validates data quality (8 rules) and reports via TCP socket
  - Pushes aggregated data to a REST API server
  - Backs up database files to Dropbox
  - Broadcasts real-time data to Bluetooth app and hub-agent via TCP socket

6. SOCKET SERVER (localhost:5555)
================================================================================

Transport: TCP
Port: 5555
Format: Newline-delimited JSON
Multiple clients supported (Bluetooth app, hub-agent, etc.)

### 6.1 Outbound Messages (meter-app-v2 broadcasts)

READING (broadcast on every meter read, ~every request_time):
  {"type":"reading","data":{...}}
  Data fields: timestamp, meter_id, meter_type, panel_id, node, data (full reading dict)

VALIDATION (broadcast on every meter read):
  {"type":"validation","data":{...}}
  Data fields: status ("OK"/"WARNING"/"CRITICAL"), score (0.0-1.0),
               checks (array), issues (array), cloud_push (bool), cloud_push_age_ms (int)

HEALTH (broadcast every 30 seconds):
  {"type":"health","data":{...}}
  Data fields: meter_connected (bool), meter_type (string),
               last_reading_age_ms (int), push_enabled (bool),
               last_push_success (bool), last_push_time (float),
               pending_push_count (int), uptime_seconds (int),
               cpu_temp (float), memory_percent (float)

ALERT (broadcast when validation is CRITICAL):
  {"type":"alert","data":{...}}
  Data fields: level ("CRITICAL"/"WARNING"), meter_id, meter_type,
               message (string), issues (array)

### 6.2 Inbound Commands (clients can send to meter-app-v2)

COMMAND format:
  {"type":"command","id":123,"action":"status"}
  {"type":"command","id":124,"action":"config_read"}
  {"type":"command","id":125,"action":"config_write","params":{...}}
  {"type":"command","id":126,"action":"reload"}

RESPONSE format:
  {"type":"response","id":123,"status":"ok","data":{...}}

Actions:
  status         Returns current health data
  config_read    Returns current config.json contents
  config_write   Writes values to config.json
  reload         Restarts the app to apply config changes

7. VALIDATION RULES
================================================================================

V1: Voltage plausibility
    AV/BV/CV must be in (90-140) OR (180-240)
    Severity: CRITICAL

V2: Frequency plausibility
    F must be 45-62 Hz
    Severity: CRITICAL

V3: Current plausibility
    Each C{n}I must be >= 0
    Severity: WARNING

V4: Power factor range
    Each C{n}PF must be 0-1.0
    Severity: WARNING

V5: Energy monotonicity
    AE/RE must not decrease between consecutive readings
    Severity: CRITICAL

V6: Zero data detection
    If all channels have I=0 for 3+ consecutive readings
    Severity: CRITICAL

V7: Spike detection
    Power (C{n}P) jumps > 10x from previous reading
    Severity: WARNING

V8: Time gap detection
    Gap between readings > 2x expected interval
    Severity: WARNING

Confidence score = ok_count / total_checks
Overall status = CRITICAL if any CRITICAL, WARNING if any WARNING, else OK

================================================================================
8. AUTO-DETECTION
================================================================================

Triggered when:
  - meters list is empty in config.json
  - auto_detect flag is true
  - meter becomes unresponsive (rescan-on-failure)

Detection strategy:
  1. Scan all serial ports
  2. For each port, try baud rates [9600, 19200, 4800, 2400]
  3. Thread-based timeout (2s) to avoid blocking on bad ports
  4. Read signature registers for each meter type:
     - PMAC211: addr 5017 (CT1 range 50-600)
     - PMAC202: addr 0 count 60 (check VTHD < 1000)
     - SPM206: addr 2201 (preset code 0-5)
     - SMP20: addr 0 count 11 (AV>100, F~5000)
     - SPM32: addr 212 (CTRatio 1-99999) + addr 42 (PTRatio > 100)
  5. Return first confirmed match per port

Supported meters for auto-detection: SPM32, PMAC211, PMAC202, SPM206, SMP20
KITT (serial JSON) cannot be auto-detected via Modbus.

  - If service is active AND last reading < 10min old: healthy

  - If service is not active: restart service
  - After 3 failed restarts: force reboot

================================================================================

File: src/watchdog.py
Service: meterapp-watchdog.service (systemd oneshot, runs every 60s)

Health check logic:
  1. Check if meterapp.service is active (systemctl is-active)
  2. Check last reading timestamp in SQLite (must be < 10 min old)
  3. If healthy: log OK, save health status
  4. If stuck: restart service
  5. If service down: restart service
  6. After 3 restart failures: sudo reboot

18. COMMON ISSUES
================================================================================

1. "Serail_Port" is intentionally misspelled — do NOT rename it
2. request_time is in MINUTES not seconds (0.1 = 6 seconds)
3. pymodbus 2.5.3 import path: pymodbus.client.sync
4. This is a 2GB ARM device — avoid pandas, numpy, heavy libraries
5. SQLite WAL mode requires -wal and -shm files alongside .db
6. Dropbox token must have files.content.write scope
7. Some Windows COM ports block on open — handled with thread timeout
8. PMAC211 detected as SPM32 when reading wrong register — use addr 5017 not 200
9. PMAC211 firmware: bulk reads from addr 0 fail (count>=2). One-by-one fallback
   reads each register individually. ~12s for 208 registers.
10. "serial" key in config: check VALUE not existence. Use info.get("serial", False)
    not "serial" in info — the key always exists (even when false).
11. API pusher: server returns HTTP 200 but body may contain 401. Check statusCode
    in response body, not just HTTP status code.
12. Orange Pi DNS: router DNS (192.168.137.1) has no recursion. Add 8.8.8.8 to
    /etc/resolv.conf for external hostname resolution.

19. PMAC211 MODBUS BEHAVIOR (Important!)
================================================================================

The PMAC211 has firmware quirks that affect Modbus RTU reads:

  - Address 0: Only count=1 works. count>=2 returns 0 or no response.
  - Addresses 35, 70, 105, 200, 264: Bulk reads work (count=34-35).
  - After failed bulk read on addr 0: subsequent reads fail until reconnect.
  - Reading payloads: [0/35, 35/35, 70/35, 105/35, 200/34, 264/34]
  - One-by-one fallback: ~12s for 208 registers (6 blocks × 35 reads × 0.03s)

The modbus.py _read_payload() method handles this:
  1. Try bulk read first
  2. If bulk fails or returns wrong count → read one-by-one
  3. Failed individual registers get value 0 (dead register)
  4. Continue reading remaining registers (don't abort)

Auto-detect uses register 5017 (CT1) which always works with count=1.

20. API PUSH BEHAVIOR
================================================================================

URL: https://tools.ampenergy.ae/data
Schedule: minutes [:03, :18, :33, :48] past each hour
Format: JSON with reading_time, panelid, channel_count, total, channels

The server returns HTTP 200 but the response body may contain:
  {"azurestatus": 401, "errors": {"API2": "Panel not registered."}}

The api_pusher.py checks statusCode in the response body:
  - If statusCode == 200: mark as "sent"
  - If statusCode != 200: mark as "failed", will retry next cycle

Records marked as "sent" will NOT be re-pushed even if the server
rejected them (401). When the panel is registered on the Azure backend,
only NEW records will be pushed.
